## What this is

**varsha** is a portable Laragon-like local web dev stack for Windows (Python 3.12 + PySide6). `README.md` is the full phased spec. It still says "VStack": read `vstack.exe` as `varsha.exe`, `vstack-helper.exe` as `megha.exe` (the UAC admin helper, Phase 3+) and `src\vstack\` as `src\varsha\`. Names are plain lowercase. Work **phase by phase** and stop after each phase for the user's OK. Done: Phase 1 (service manager), the tunnel bonus, Phase 2 (configs, DB setup, phpMyAdmin, backups) and Phase 3 (sites, SSL, hosts, DNS, megha), remote databases and Phase 4 (per-site PHP, php.ini editor, terminal, Quick Create, site delete, tray menu), then the extras: Mailpit inbox, scheduled backups and tasks, the database import wizard, the PHP error watcher, Doctor, git status on site cards, LAN share (with QR), Quick Create "Link a folder", MDB Rescue, MySQL Rescue, the grouped top bar, the Data page (shown as **Data Browser**) phases A (SQLite files), C (Access, read-only) and B (CSV/TSV), the Settings page batches 1 (start with Windows, auto-start services, panel port), 2 (open the panel on start, what Quit does, PHP timezone, backup folder, tray notifications) and 3 (11 site TLD behind a warning, 10 log size, 12 export/import, 9 crash restarts and timeouts), the top bar's Restart button (all running services) and the Apache card's Reload button (graceful). Next, only if asked: Data page phase D (optional: json/dbf; xlsx needs a download, ask). Background workers are postponed until a project needs one. Personal, machine-specific notes (local paths, source folders, the owner's projects) live in `CLAUDE.local.md`, which is git-ignored: keep them out of this public file. **varsha is for personal use: no internet downloads, no auto-update** (the README's Phase 5 downloads and Phase 6 updater are dropped; new versions are added from folders already on the PC). Update this line when a phase finishes.

User requests beyond the README:
- **The UI is a browser control panel, not Qt windows** (the user's choice: neo-brutalism with a Bento home grid). Qt is used only for the tray icon. Keep that look.
- DB ports are the user's choice (changed by them on 2026-11-04): **MariaDB 11.8 = 3306, MySQL 8.4 = 3307, MySQL 5.6 = 3308**. Don't change them. Laragon's own MySQL also uses 3306, so it can't run at the same time as varsha's MariaDB.
- **The start page** (`http://localhost/`) is `etc/templates/start-page.php`, the one to edit (`www\` is git-ignored). `AppPaths.seed_start_page()` copies it to `www\index.php` at startup when missing, and updates it only while that file is still the exact copy varsha wrote (SHA-256 in `data\start-page.sha256`), so a user's own or edited page is never overwritten. It must keep working on PHP 5.4.

## Commands

The repository checkout is the **development copy** (source, tests, tools, its own bin/config/data/www for running from source). C:\Varsha is the **deployed app only**: `Varsha.exe` + `_internal\` (PyInstaller one-folder build) + `bin\`, plus the config/data/www/logs/etc folders varsha creates itself. Never put the venv, source or tests in C:\Varsha. **Every implementation happens in the checkout first; once it is successful there (tests pass, verified in the dev instance), deploy it to C:\Varsha with `tools\deploy.cmd`.** The bare `python` command on this machine is the Microsoft Store stub; use the venv (create venvs with `py -3.12`).

```powershell
tools\test.cmd                                    # all tests (.venv\Scripts\python -m pytest -q)
tools\test.cmd tests\test_manager.py -k crash     # a subset
tools\deploy.cmd                                  # PyInstaller build (tools\varsha.spec) -> C:\Varsha: Varsha.exe + _internal, bin\ synced (new/changed only); refuses while anything runs from C:\Varsha
tools\deploy.cmd --skip-build                     # reuse the last PyInstaller build
tools\deploy.cmd --no-install                     # only refresh setup\ (installer + payload)
setup\Setup.exe                            # the installer: fresh install / update of C:\Varsha (works on a formatted PC)
tools\run-dev.cmd                                 # run from source against the checkout's own folders (or .venv\Scripts\python -m varsha)
```

There is no linter or type checker configured yet. Tests cover only non-GUI logic. Manager tests run a real TCP stand-in (`tests/fake_service.py`) and build `ServiceManager` with an injected `locator` that returns the base Python as the "installed binary" (see the `make_manager` fixture and `fake_def()` in `tests/conftest.py`). Use that pattern for new service tests rather than needing real binaries.

`.venv\Scripts\python -m varsha --no-browser` runs the tray and panel without opening a tab. The login URL (with its token) is in `%LOCALAPPDATA%\varsha\panel-<hash>.json`; drive the panel through its HTTP API (`tests/test_panel.py` shows how). To screenshot it headless, use `QWebEngineView` with `QT_QPA_PLATFORM=offscreen`, `QT_QPA_FONTDIR=C:/Windows/Fonts` and `QTWEBENGINE_CHROMIUM_FLAGS=--disable-gpu`. `node --check src/varsha/web/static/app.js` catches JS syntax errors. Never write a source file with a Python script that might raise mid-`write_text`: it truncates the file (this happened to app.js).

## Architecture

- **Everything is relative to the root folder** (`varsha/paths.py`: `VARSHA_ROOT` env var, else frozen exe dir, else repo root). No module builds paths from drive letters. `services.json` rejects absolute paths and `..`.
- **Config-driven services.** `config/services.json` → `services/config.py` (strict validation, `_`-prefixed keys are comments) → `ServiceDef`. Adding a service or another DB version is a JSON edit only. `exe` is a glob such as `bin/mysql/mysql-8.4*/bin/mysqld.exe`. `services/resolve.py` picks the newest match, reads the version from the folder name, and expands `{placeholders}` (`{home}`, `{config}`, `{data_dir}`, `{ports[N]}`, …) to forward-slash paths. Unknown placeholders fail at load time.
- **`services/manager.py` has no Qt.** Its blocking methods run on worker threads, with one `RLock` per service. A monitor thread polls processes, auto-restarts crashes (`max_auto_restarts`, counter reset after `stable_after`), and skips services whose lock is held. On launch, `adopt_running()` takes over processes left from an earlier session, matched by exe path *inside the root only*, so Laragon/WAMP processes are never touched. State changes go out through a listener callback with the service id.
- **Control panel** (`web/`): `server.py` is a stdlib `ThreadingHTTPServer` on 127.0.0.1:`panel_port` (7700). Security: Host header allow-list (anti DNS rebinding); a per-run token swapped for an HttpOnly SameSite=Strict cookie; every POST needs `X-Varsha: 1` plus a same-origin `Origin`; strict CSP (no inline JS or style attributes, so set widths with `el.style`); `/api/open` takes folder *keywords*, never paths. `panel.py` (`PanelApp`) holds the actions; long ones run via `run_task` and report through an SSE `EventBus` (`state` → the page refetches `/api/state`; `toast`). The frontend in `web/static/` is vanilla JS (no build step). **Top bar** (the user's layout): daily pages are buttons (Stack, Sites, Databases, Mail, Errors, Logs); the rest sit in two menus, **Tools** (Data Browser, MDB Rescue, MySQL Rescue, Tasks, Share) and **System** (System, Doctor, Settings), in `index.html`. Menu buttons carry `data-nav-menu` (not `data-view`, which the global click handler treats as navigation); `renderShell()` shows "Tools: Data Browser" plus the summed badges on the menu button, and `setNavMenu()` opens and closes them (click outside, Escape, navigating). Keys 1–0 use the fixed `SHORTCUTS` list. The home view refreshes its Bento tiles in place so the live log and inputs survive updates. `gui/app.py` wires everything; `gui/tray.py` is the only Qt UI.
- **Sites** (`sites/`): `discovery.py` maps each `www\<folder>` to `<slug>.<tld>` (`public\` is the docroot if present; overrides in `config/sites.json`). `SiteManager` watches `www\` (top level only, debounced), regenerates `etc/apache/sites-enabled/*.conf` and calls `manager.reload("apache")`, which runs `httpd -t` and then a graceful restart through the `ap<pid>_restart` event. It deletes only vhost files that start with `# varsha-generated`. HTTPS certificates come from `bin\mkcert\mkcert.exe` (cached per name set; the CA stays in the user's own CAROOT). Without mkcert, sites are HTTP-only, but port 443 is still opened.
- **megha** (`helper/megha.py`, launched elevated by `helper/elevate.py` via `ShellExecuteExW("runas")`): the only code that runs as admin. It edits the hosts block between `# varsha-start/-end` (backup `hosts.varsha.bak`, names validated to end in the TLD, path never configurable) and adds or removes an NRPT rule sending `.test` to 127.0.0.1. The DNS server itself (`dns/server.py`, a built-in service with `"module"`) runs unprivileged, because Windows has no privileged ports. Built-in services are adopted by command line, never by exe, since python.exe would match varsha itself.
- **PHP per site + php.ini editor** (Phase 4): `sites.json` `"php": "5.4"` is a version prefix resolved by `ConfigEngine.find_php` (newest match, x64 preferred). `vhost.conf.j2` then adds a per-vhost `FcgidWrapper` plus `FcgidInitialEnv PHPRC/PATH` for that build; the default PHP stays server-wide in httpd.conf. Extension toggles and ini directives live in `config/php.json` (`php/config.py`). Only differences from the defaults are stored, and they're rendered into the generated php.ini (`zend_extension` for opcache/xdebug; user directives at the end, so they win; `LOCKED_KEYS` can't be changed). mbstring must load before exif on PHP 5. `ConfigEngine.check_php` starts php.exe once to report extension load warnings. `devtools.py` covers the terminal (WT/cmd plus a generated `etc/shims/varsha-env.cmd`, because Windows Terminal doesn't inherit the caller's env), Quick Create (blank / "Link a folder" / WordPress zip with a zip-slip check, plus DB creation; Laravel was removed at the user's request), and deleting a site (SHFileOperation to the Recycle Bin; databases are kept). "Link a folder" makes a junction `www\<name>` → an existing project folder with `_winapi.CreateJunction` (no admin, no console) and never writes into the project; the source must be an absolute folder outside the varsha root and not a drive root. **Deleting a linked site only removes the junction** (`os.rmdir`), never the target: never call `resolve()` on a www entry before checking `is_junction()`, because it follows the link. The panel's "Browse…" is a native folder dialog: `/api/pick-folder` → `PanelApp.folder_picker` → a queued `_MainThread.pick_folder` signal runs `QFileDialog` on the Qt thread (always-on-top owner widget), and the HTTP thread waits on an Event.
- **Remote DBs** (`services/remote.py`): `config/remote-databases.json` has no passwords; passwords are DPAPI-encrypted under `remote:<id>`. With `remember`, phpMyAdmin uses `auth_type=config`, reading the password from `data/phpmyadmin/remote-secrets.php`, which `restrict_to_current_user` locks to SYSTEM and the current user with icacls. `test_connection` uses the MySQL 8 client (`--ssl-mode`), else MariaDB's.
- **Varsha.exe** (deployed) is a PyInstaller one-folder build (`tools\varsha.spec`, windowed, the user's icon). Templates, `web\static` and default `services.json`/`settings.json` are bundled in `_internal`; `paths.bundle_dir()` finds them, `AppPaths.templates` prefers `<root>\etc\templates` when that exists (source checkout, tests), and `seed_config()` copies the default config into a fresh folder. A frozen exe can't do `python -m`, so built-in services and megha run as `Varsha.exe --run-module varsha.<module>` (`__main__.py`, varsha modules only); adoption matches `-m` or `--run-module`. `Varsha.exe --version` prints the version and root (deploy's check).
- **Installer** (`tools\installer\Setup.cs`, compiled with the .NET Framework csc.exe that ships with Windows): `setup\Setup.exe` in the checkout + `payload\` (the build + `bin\` as hard links to the repo's bin). It installs to C:\Varsha (window, or `/quiet /target DIR /noshortcuts /log FILE`), copies `_internal` as a whole and bin new/changed only, creates shortcuts, refuses while anything runs from the target, and never touches config/data/www (varsha itself writes the start page on first run). It works on a freshly formatted PC: the VC++ runtimes (vcruntime140/msvcp140 x64, VC90 x86 for PHP 5.4.16) were copied app-local into `bin\` next to httpd, php-cgi and mysqld. `tools\launcher\Varsha.cs` is the old dev launcher (starts `.venv\Scripts\pythonw -m varsha` from its own folder); it is not deployed.
- **Tunnels** (`tunnel/`, the README "Bonus" feature, built early at the user's request): `TunnelManager` runs `bin\cloudflared\cloudflared.exe tunnel --url …` quick tunnels (no Cloudflare account). It is separate from `ServiceManager` because tunnels are created on demand and are not in `services.json`. `parse_target` accepts only localhost, 127.x or `*.test`. The origin is always `127.0.0.1`, and the typed host goes in `--http-host-header` so Apache vhosts still match. Tunnels never outlive varsha: `stop_all` runs on exit even with "leave running", and `kill_orphans` runs at startup. The GUI is `gui/share_dialog.py`.
- **Data page** (the user named it **Data Browser** in the UI; `data/sqlite_files.py` + `web/static/data.js`, which manages its own page; app.js only builds the skeleton once so state refreshes never reset it): SQLite files are picked in a native file dialog (`/api/data/pick` → `PanelApp.pick_data_file` → the `_MainThread.pick_folder` signal in "file" mode) or from the recent list / a scan of `www\*` (and a junctioned `public\`'s project folder); the panel only sends 16-hex file ids, never paths. Files open with `mode=ro`; Edit mode is per file and per session, and the first write takes a backup with SQLite's backup API (WAL-safe) into `data/file-backups/<stem>-<id>/` (millisecond names, never overwritten, 20 kept); Restore copies back with the backup API after backing up the current state. Table/column names are matched against the file's own schema and always quoted; an authorizer denies ATTACH/DETACH, and the SQL box refuses VACUUM/ATTACH (the Vacuum button lifts the authorizer for its own connection, since VACUUM attaches internally). Files inside varsha's `data\` are refused. Values travel as `{"t": null|int|real|text|blob, "v"}` (big ints as strings, text cut at 2000 chars with `more`). A script in the SQL box runs as one transaction in Edit mode; read-only lets SQLite itself refuse writes. **Access files** (`data/access_files.py` + `data/access_odbc.py`): the Access ODBC driver on this PC is 32-bit only, so each request runs `access_odbc.py` (stdlib + ctypes over odbc32.dll, no varsha imports; bundled as a plain .py data file in the spec) under an installed 32-bit Python (`find_python32`: `VARSHA_PYTHON32`, `bin\python32*\`, `%LOCALAPPDATA%\Programs\Python\Python3*-32\`, Program Files (x86)) with JSON on stdin/stdout. ODBC calls return a 16-bit SQLRETURN, so every function's `restype` must be `c_short` (otherwise every call looks failed). The user's file is never opened: Access writes a `.ldb` next to any file it opens, so it reads a copy in `data/access-cache/<id>.mdb`, refreshed when size or mtime change. Connections are `ReadOnly=1` plus `SQL_MODE_READ_ONLY`, only SELECT/TRANSFORM run, and every write action refuses Access files. Access SQL has no OFFSET: pages use `TOP offset+limit` and skip rows; search uses `([col] & '') LIKE '%x%'`. `tests/make_access_fixture.py` builds real .mdb/.accdb fixtures with the driver's `CREATE_DB` / `CREATE_DBV12` (plain CREATE_DB always writes Jet format). **CSV/TSV** (`data/csv_files.py`): a CSV is parsed (encoding from BOM/UTF-8/cp1252, delimiter by `csv.Sniffer`, header guessed, line ending from the first chunk; read through `io.StringIO(text, newline="")` so quoted line breaks survive) into a SQLite cache `data/csv-cache/<id>.sqlite`, rebuilt when size/mtime change, and the SQLite code serves it (`connect()` swaps in the cache path). A column becomes INTEGER/REAL only if every value round-trips to the identical text (`str(int(v)) == v`, `repr(float(v)) == v`), so `007` or `1200.50` stay text and an unchanged save is byte-identical. Writes go through `_write()` into the cache and then `write_back()` rewrites the CSV with the original delimiter, quoting (QUOTE_MINIMAL), encoding/BOM, newline and header texts; the first change copies the original to file-backups. The SQL box is SELECT-only for CSV (edits happen in the grid); files over 50 MB are read-only; Drop/Vacuum/Export .sql don't apply.
- **MDB Rescue** (`data/rescue.py` + `data/rescue_runner.py` + `web/static/rescue.js`, Tools menu): the owner's own MDB rescue tool is copied into `bin\mdb-rescue\` with `tools\sync-mdb-rescue.cmd <source>` (app, its portable `runtime\python64/32`, docs; never jobs/tests/.git/settings) and is never modified. Each job runs `rescue_runner.py` (stdlib, bundled as a plain .py) under the tool's python64; it calls the tool's `run_pipeline(...)` and streams JSON lines (job, progress, log, done). Stop = `stop` on stdin (or stdin closing) -> the tool's own `cancel_event`, so it stops at a safe point and still writes its report. One job at a time; progress goes out as SSE `rescue` events (throttled ~0.4 s). Presets match the tool's window (recommended/raw/carve/diagnose; `export` added when .sql or .mdb is ticked). Results live in `data/mdb-rescue-jobs/`, the one data subfolder the Data page may open (recovered .sqlite, rebuilt/repaired .mdb). "Import into MariaDB" (`DatabaseManager.import_into`) always creates a NEW database and refuses an existing name. The original file is only read by the tool (it copies it with a SHA-256 check).
- **MySQL Rescue** (`data/mysql_rescue.py` + `data/mysql_rescue_runner.py` + `web/static/mysqlrescue.js`, Tools menu): the owner's MySQL rescue tool (its own repo; it is ours to change) is copied into `bin\mysql-rescue\` with `tools\sync-mysql-rescue.cmd <source>` (app, runtime, docs; never jobs/tests/servers/settings). `MysqlRescueManager` subclasses `RescueManager` (class attributes + `_check_target`/`_prepare`/`_summary`/`_detail`); routes are `/api/(rescue|mysql-rescue)/...`, SSE events `mysql_rescue`. A data folder is picked in the native folder dialog; a folder of a running varsha database (`PanelApp._live_data_dirs`) is refused, also at Start. varsha passes its own `bin\mysql` and `bin\mariadb` as server folders. The tool copies the folder, starts a temporary server on a copy (skip-grant-tables, loopback / named pipe, innodb_force_recovery 0-6 as needed), dumps table by table, REPAIRs MyISAM/Aria on the copy, reads damaged InnoDB tables around bad pages in primary-key ranges, and writes one `<db>.sql` per database without CREATE DATABASE, so "Import" (`rescue_import(..., key="sql:<db>")`) loads it into a NEW database. Jobs: `data/mysql-rescue-jobs/` with the same Browse / Clean / Full clean.
- **Settings page** (`app_settings.py` + `web/static/settings.js`, System menu): the Run key entry ("varsha" / "varsha (dev)", `--startup` = quiet), auto-start flags written into services.json, the panel port (restart via `restart_command`). Batch 2 keys in settings.json: `open_panel_on_start`, `quit_action` (ask/stop/leave; the panel's Quit button reads it from /api/state, the tray always offers both), `php_timezone` (checked against the default php.exe's `timezone_identifiers_list()`; Apache reloads if running), `backup_dir` (created and write-tested, never inside www\), `tray_notifications` {failures, php_errors, mail}. `PanelApp._apply_settings` writes the file and replaces the settings in the panel, manager and engine at once (panel_port is never changed there). Batch 3: `set_tld` (stops tunnels and LAN shares, renames ignored PHP-error sites and site-tied tasks, then a task re-syncs vhosts/certs, restarts DNS, rewrites hosts and moves the DNS route; the DNS service reads the TLD from settings.json when it gets no `--tld`, since deployed copies keep their own services.json; tunnels take `TunnelManager.tld`); `log_max_mb` with `proc_utils.trim_logs` (at start and every 10 min in the monitor loop; a log held open is copy-truncated to `.log.1`); `settings_transfer.py` (export zip of the config files + manifest, never credentials; import reads only known top-level names, validates each like varsha loads it, backs up to `data/settings-backups/`, then restarts). Item 9: `max_auto_restarts` 0-10, `start_timeout_seconds` 5-600, `stop_timeout_seconds` 5-300 (`set_service_timing`; the manager reads them live). The page is a 2-column grid of 10 cards (3 columns from 1800px, 1 under 1180px).
- **LAN share** (`sites/lan.py`, Share page + site cards): one extra HTTPS vhost per shared site (`etc/apache/lan-enabled/<domain>.conf` from `lan.conf.j2`) with `Listen 0.0.0.0:<port>` from 8443–8462 (each site gets its old port back, `data/lan-ports.json`). It serves the same docroot with **no proxy**: `RequestHeader set Host <domain> early` keeps apps that only answer on their APP_URL host working, `mod_substitute` rewrites `https://<domain>` links (also JSON-escaped `https:\/\/`) to the LAN address, and `Header edit Location` does the same for redirects. Because nothing is proxied, PHP sees the colleague's real IP, so phpMyAdmin's `Require local` still refuses them. Inside quoted Apache arguments `\\` becomes `\`, so the template writes `\\\\` to get a literal backslash in a regex (verified with httpd 2.4.68). Shares are runtime state: `lan_stop_all()` runs at startup (crash leftovers) and on quit even when services stay up. The cert is mkcert's for the LAN IPs plus the computer name (colleagues accept a warning once). Firewall: megha `firewall-lan-add` adds one rule "varsha LAN share" for this root's `bin\…\httpd.exe` on the port range, private and domain profiles; a Public network profile is reported in the panel, never changed. A graceful restart opens and closes the extra Listen ports on Windows.
- **Config engine** (`config_engine/engine.py`, Phase 2): it is passed to `ServiceManager` as the `prepare` hook and runs before every start. It renders `etc/templates/*.j2` with jinja2 (`StrictUndefined`) into `etc/…` and `bin/phpmyadmin/config.inc.php` + `config.footer.inc.php`. A file is rewritten only when its content changes, and the old copy is kept as `.bak`. Starting Apache also regenerates one `etc/php/<build folder>/php.ini` per PHP build (only extensions whose DLL exists) and the phpMyAdmin config. Its server list comes from the DB services, sorted by port, plus `settings.json` `phpmyadmin_extra_servers`. `config.footer.inc.php` is phpMyAdmin's official custom-footer hook; varsha uses it for the "Quick login" panel on the login page (live port check per server, one-click root login).
- **First-time DB setup**: when `data_dir` is empty, the manager runs `init_command`, fed with `init_stdin` (`sql:` literals or files). MySQL 5.6 has no `--initialize`, so it uses `--bootstrap` with its share/*.sql files, as its `mysql_install_db.pl` does. A failed setup is renamed to `<dir>.failed-<time>`, never deleted.
- **DB credentials** (`secrets.py`): root passwords are DPAPI-encrypted in `data/credentials.json` and reach mysql/mysqladmin/mysqldump only through a temporary `[client]` option file in `%TEMP%` (`{client_cnf}`), never on the command line. `reset_root_password` restarts once with `--init-file`. That file runs **one statement per line**, so `password_reset_sql` is a list (joined with newlines) and `sql_string_body` escapes newlines. Backup/restore/HeidiSQL live in `services/database.py`, and the row ⋯ menu is `gui/service_menu.py`.
- **Stop methods** (`stop.method`): `command` (e.g. `mysqladmin shutdown`; a missing exe or non-zero exit means kill right away), `apache_signal`, `terminate`. Every method falls back to `kill_tree` after `stop_timeout`. `stop.also_kill` names child processes to kill right after the graceful request: Apache uses it for `php-cgi.exe`, because mod_fcgid otherwise waits ~10 s for its workers.

## Windows gotchas already handled (keep them)

- Never call `app.quit()` (or any PySide call that waits on the Qt thread) from a worker thread: it holds the GIL while waiting, and deadlocks with a Qt thread waiting on the GIL (it hung quit whenever no services needed stopping). Emit a queued signal instead (`_MainThread.exit_loop`). On quit, `arm_quit_watchdog` sets a faulthandler C-level timer (works even with the GIL held) that dumps all stacks to `logs/varsha-hang.log` and force-exits after 150 s (`VARSHA_QUIT_DEADLINE`).

- Console Apache ignores `httpd -k stop`, which only reaches a Windows *service*. `signal_apache_shutdown` sets the named event `ap<parent pid>_shutdown` (verified with httpd 2.4.68). Apache's child `httpd.exe` holds the ports, so always kill the whole tree.
- Port checks use psutil LISTEN entries plus a plain `bind()` test: no `SO_REUSEADDR` (it would steal ports) and no `SO_EXCLUSIVEADDRUSE` (it fails on TIME_WAIT). WinError 10013 means a Hyper-V/WSL excluded port range, and PID 4 means http.sys/IIS.
- In a venv, `sys.executable` is a launcher that spawns the real python as a child. Tests use `sys._base_executable` so the PID owns the port.
- MySQL `--defaults-file` must be the first argument. Option files treat `\` as an escape character, which is why placeholders expand with `/`.
- cloudflared prints the trycloudflare link *before* the tunnel is registered, and the new name takes 10–15 s to reach DNS. Opening it early makes Windows cache NXDOMAIN for minutes. So `start()` waits for "Registered tunnel connection" and then for the name to resolve through Cloudflare DNS-over-HTTPS (not the system resolver, which would poison the cache). cloudflared also logs an ERR for an empty `--config` file, so `etc\cloudflared\quick-tunnel.yml` contains `no-autoupdate: true`.
- mod_fcgid starts php-cgi with an almost empty environment. Without `SystemRoot`, PHP's random_bytes/openssl/curl fail. Its default `FcgidMaxRequestLen` (128 KB) breaks uploads and phpMyAdmin imports. Both are set in `httpd.conf.j2`. Apache and MySQL listen on loopback only. `/phpmyadmin` refuses requests carrying `CF-Connecting-IP`, because tunnel traffic arrives from 127.0.0.1 and would otherwise pass `Require local`.
- watchdog on Windows reports a deleted *folder* as a `FileDeletedEvent` (is_directory False), so the www watcher must not filter on is_directory.
- The Laragon Apache build pairs mod_ssl (built for OpenSSL 3.6.3) with 3.0.21 DLLs, which logs AH01882 at every start. It's harmless and needs matching DLLs from Apache Lounge to fix.
- Child stdout/stderr go straight to `logs\<id>.log` through an inherited handle, so logs keep flowing after varsha exits.

## Binaries and local sources

`bin\` is filled by hand from binaries already on the PC and is git-ignored (where each one came from is in `CLAUDE.local.md`): Apache 2.4.68, PHP 8.5.12 / 8.3.33, 5.4.16 and 5.4.33 NTS x86, MySQL 8.4.3, MariaDB 11.8.9, MySQL 5.6.12 32-bit, Mailpit, Composer, HeidiSQL, phpMyAdmin 5.2.3, cloudflared 2026.10.7 (official GitHub release, Authenticode-signed by Cloudflare, Inc.) and mkcert 1.4.4 (official release; SHA-256 d2660b50…1398 matched both the Scoop and winget manifests). The mkcert CA is installed in the user's Windows Root store (CAROOT `%LOCALAPPDATA%\mkcert`). `mkcert -install` exits 1 when a JDK is installed, because it also tries the JDK's cacerts file, which needs admin; `trust_https` treats the Windows-store success as enough. Also `mod_fcgid.so` (VS18 build) in the Apache modules folder and the Mozilla CA bundle at `bin\ca\cacert.pem`. Copied `php.ini` files were renamed to `php.ini.<source>` and kept as references; the real ones are generated. **Never write to another stack's data folder (Laragon, WAMP, …) or any other source folder**: those are live databases; the import wizard only reads copies. Laragon's own MySQL also uses 3306, so it and varsha's MariaDB can't run at the same time; the port check reports the clash.
