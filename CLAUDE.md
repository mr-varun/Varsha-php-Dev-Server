## What this is

**varsha** is a portable Laragon-like local web dev stack for Windows (Python 3.12 + PySide6). `README.md` is the full phased spec. It still says "VStack": read `vstack.exe` as `varsha.exe`, `vstack-helper.exe` as `megha.exe` (the UAC admin helper, Phase 3+) and `src\vstack\` as `src\varsha\`. Names are plain lowercase. Work **phase by phase** and stop after each phase for the user's OK. Done: Phase 1 (service manager), the tunnel bonus, Phase 2 (configs, DB setup, phpMyAdmin, backups) and Phase 3 (sites, SSL, hosts, DNS, megha), remote databases and Phase 4 (per-site PHP, php.ini editor, terminal, Quick Create, site delete, tray menu). Next: see below. **varsha is for personal use: no internet downloads, no auto-update** (the README's Phase 5 downloads and Phase 6 updater are dropped; new versions are added from folders already on the PC). Update this line when a phase finishes.

User requests beyond the README:
- **The UI is a browser control panel, not Qt windows** (the user's choice: neo-brutalism with a Bento home grid). Qt is used only for the tray icon. Keep that look.
- DB ports are the user's choice (changed by them on 2026-11-04): **MariaDB 11.8 = 3306, MySQL 8.4 = 3307, MySQL 5.6 = 3308**. Don't change them. The user's client projects (D:\Work\Websites\example-monorepo\*\.env) use MariaDB on DB_PORT=3306. Laragon's own MySQL also uses 3306, so it can't run at the same time as varsha's MariaDB.

## Architecture

- **Everything is relative to the root folder** (`varsha/paths.py`: `VARSHA_ROOT` env var, else frozen exe dir, else repo root). No module builds paths from drive letters. `services.json` rejects absolute paths and `..`.
- **Config-driven services.** `config/services.json` → `services/config.py` (strict validation, `_`-prefixed keys are comments) → `ServiceDef`. Adding a service or another DB version is a JSON edit only. `exe` is a glob such as `bin/mysql/mysql-8.4*/bin/mysqld.exe`. `services/resolve.py` picks the newest match, reads the version from the folder name, and expands `{placeholders}` (`{home}`, `{config}`, `{data_dir}`, `{ports[N]}`, …) to forward-slash paths. Unknown placeholders fail at load time.
- **`services/manager.py` has no Qt.** Its blocking methods run on worker threads, with one `RLock` per service. A monitor thread polls processes, auto-restarts crashes (`max_auto_restarts`, counter reset after `stable_after`), and skips services whose lock is held. On launch, `adopt_running()` takes over processes left from an earlier session, matched by exe path *inside the root only*, so Laragon/WAMP processes are never touched. State changes go out through a listener callback with the service id.
- **Control panel** (`web/`): `server.py` is a stdlib `ThreadingHTTPServer` on 127.0.0.1:`panel_port` (7700). Security: Host header allow-list (anti DNS rebinding); a per-run token swapped for an HttpOnly SameSite=Strict cookie; every POST needs `X-Varsha: 1` plus a same-origin `Origin`; strict CSP (no inline JS or style attributes, so set widths with `el.style`); `/api/open` takes folder *keywords*, never paths. `panel.py` (`PanelApp`) holds the actions; long ones run via `run_task` and report through an SSE `EventBus` (`state` → the page refetches `/api/state`; `toast`). The frontend in `web/static/` is vanilla JS (no build step). The home view refreshes its Bento tiles in place so the live log and inputs survive updates. `gui/app.py` wires everything; `gui/tray.py` is the only Qt UI.
- **Sites** (`sites/`): `discovery.py` maps each `www\<folder>` to `<slug>.<tld>` (`public\` is the docroot if present; overrides in `config/sites.json`). `SiteManager` watches `www\` (top level only, debounced), regenerates `etc/apache/sites-enabled/*.conf` and calls `manager.reload("apache")`, which runs `httpd -t` and then a graceful restart through the `ap<pid>_restart` event. It deletes only vhost files that start with `# varsha-generated`. HTTPS certificates come from `bin\mkcert\mkcert.exe` (cached per name set; the CA stays in the user's own CAROOT). Without mkcert, sites are HTTP-only, but port 443 is still opened.
- **megha** (`helper/megha.py`, launched elevated by `helper/elevate.py` via `ShellExecuteExW("runas")`): the only code that runs as admin. It edits the hosts block between `# varsha-start/-end` (backup `hosts.varsha.bak`, names validated to end in the TLD, path never configurable) and adds or removes an NRPT rule sending `.test` to 127.0.0.1. The DNS server itself (`dns/server.py`, a built-in service with `"module"`) runs unprivileged, because Windows has no privileged ports. Built-in services are adopted by command line, never by exe, since python.exe would match varsha itself.
- **PHP per site + php.ini editor** (Phase 4): `sites.json` `"php": "5.4"` is a version prefix resolved by `ConfigEngine.find_php` (newest match, x64 preferred). `vhost.conf.j2` then adds a per-vhost `FcgidWrapper` plus `FcgidInitialEnv PHPRC/PATH` for that build; the default PHP stays server-wide in httpd.conf. Extension toggles and ini directives live in `config/php.json` (`php/config.py`). Only differences from the defaults are stored, and they're rendered into the generated php.ini (`zend_extension` for opcache/xdebug; user directives at the end, so they win; `LOCKED_KEYS` can't be changed). mbstring must load before exif on PHP 5. `ConfigEngine.check_php` starts php.exe once to report extension load warnings. `devtools.py` covers the terminal (WT/cmd plus a generated `etc/shims/varsha-env.cmd`, because Windows Terminal doesn't inherit the caller's env), Quick Create (blank / `composer create-project` / WordPress zip with a zip-slip check, plus DB creation), and deleting a site (SHFileOperation to the Recycle Bin; databases are kept).
- **Remote DBs** (`services/remote.py`): `config/remote-databases.json` has no passwords; passwords are DPAPI-encrypted under `remote:<id>`. With `remember`, phpMyAdmin uses `auth_type=config`, reading the password from `data/phpmyadmin/remote-secrets.php`, which `restrict_to_current_user` locks to SYSTEM and the current user with icacls. `test_connection` uses the MySQL 8 client (`--ssl-mode`), else MariaDB's.
- **Varsha.exe** (deployed) is a PyInstaller one-folder build (`tools\varsha.spec`, windowed, the user's icon). Templates, `web\static` and default `services.json`/`settings.json` are bundled in `_internal`; `paths.bundle_dir()` finds them, `AppPaths.templates` prefers `<root>\etc\templates` when that exists (source checkout, tests), and `seed_config()` copies the default config into a fresh folder. A frozen exe can't do `python -m`, so built-in services and megha run as `Varsha.exe --run-module varsha.<module>` (`__main__.py`, varsha modules only); adoption matches `-m` or `--run-module`. `Varsha.exe --version` prints the version and root (deploy's check).
- **Installer** (`tools\installer\Setup.cs`, compiled with the .NET Framework csc.exe that ships with Windows): `D:\…\Varsha-Setup\Setup.exe` + `payload\` (the build + `bin\` as hard links to the repo's bin). It installs to C:\Varsha (window, or `/quiet /target DIR /noshortcuts /log FILE`), copies `_internal` as a whole and bin new/changed only, creates shortcuts, refuses while anything runs from the target, and never touches config/data/www. It works on a freshly formatted PC: the VC++ runtimes (vcruntime140/msvcp140 x64, VC90 x86 for PHP 5.4.16) were copied app-local into `bin\` next to httpd, php-cgi and mysqld. `tools\launcher\Varsha.cs` is the old dev launcher (starts `.venv\Scripts\pythonw -m varsha` from its own folder); it is not deployed.
- **Tunnels** (`tunnel/`, the README "Bonus" feature, built early at the user's request): `TunnelManager` runs `bin\cloudflared\cloudflared.exe tunnel --url …` quick tunnels (no Cloudflare account). It is separate from `ServiceManager` because tunnels are created on demand and are not in `services.json`. `parse_target` accepts only localhost, 127.x or `*.test`. The origin is always `127.0.0.1`, and the typed host goes in `--http-host-header` so Apache vhosts still match. Tunnels never outlive varsha: `stop_all` runs on exit even with "leave running", and `kill_orphans` runs at startup. The GUI is `gui/share_dialog.py`.
- **Config engine** (`config_engine/engine.py`, Phase 2): it is passed to `ServiceManager` as the `prepare` hook and runs before every start. It renders `etc/templates/*.j2` with jinja2 (`StrictUndefined`) into `etc/…` and `bin/phpmyadmin/config.inc.php` + `config.footer.inc.php`. A file is rewritten only when its content changes, and the old copy is kept as `.bak`. Starting Apache also regenerates one `etc/php/<build folder>/php.ini` per PHP build (only extensions whose DLL exists) and the phpMyAdmin config. Its server list comes from the DB services, sorted by port, plus `settings.json` `phpmyadmin_extra_servers`. `config.footer.inc.php` is phpMyAdmin's official custom-footer hook; varsha uses it for the "Quick login" panel on the login page (live port check per server, one-click root login).
- **First-time DB setup**: when `data_dir` is empty, the manager runs `init_command`, fed with `init_stdin` (`sql:` literals or files). MySQL 5.6 has no `--initialize`, so it uses `--bootstrap` with its share/*.sql files, as its `mysql_install_db.pl` does. A failed setup is renamed to `<dir>.failed-<time>`, never deleted.
- **DB credentials** (`secrets.py`): root passwords are DPAPI-encrypted in `data/credentials.json` and reach mysql/mysqladmin/mysqldump only through a temporary `[client]` option file in `%TEMP%` (`{client_cnf}`), never on the command line. `reset_root_password` restarts once with `--init-file`. That file runs **one statement per line**, so `password_reset_sql` is a list (joined with newlines) and `sql_string_body` escapes newlines. Backup/restore/HeidiSQL live in `services/database.py`, and the row ⋯ menu is `gui/service_menu.py`.
- **Stop methods** (`stop.method`): `command` (e.g. `mysqladmin shutdown`; a missing exe or non-zero exit means kill right away), `apache_signal`, `terminate`. Every method falls back to `kill_tree` after `stop_timeout`. `stop.also_kill` names child processes to kill right after the graceful request: Apache uses it for `php-cgi.exe`, because mod_fcgid otherwise waits ~10 s for its workers.

## Windows gotchas already handled (keep them)

- Never call `app.quit()` (or any PySide call that waits on the Qt thread) from a worker thread: it holds the GIL while waiting, and deadlocks with a Qt thread waiting on the GIL (it hung quit whenever no services needed stopping). Emit a queued signal instead (`_MainThread.exit_loop`). On quit, `arm_quit_watchdog` sets a faulthandler C-level timer (works even with the GIL held) that dumps all stacks to `logs/varsha-hang.log` and force-exits after 150 s (`VARSHA_QUIT_DEADLINE`).

- Console Apache ignores `httpd -k stop`, which only reaches a Windows *service*. `signal_apache_shutdown` sets the named event `ap<parent pid>_shutdown` (verified with httpd 2.4.68). Apache's child `httpd.exe` holds the ports, so always kill the whole tree.
- Port checks use psutil LISTEN entries plus a plain `bind()` test: no `SO_REUSEADDR` (it would steal ports) and no `SO_EXCLUSIVEADDRUSE` (it fails on TIME_WAIT). WinError 10013 means a Hyper-V/WSL excluded port range, and PID 4 means http.sys/IIS.
- In a venv, `sys.executable` is a launcher that spawns the real python as a child. Tests use `sys._base_executable` so the PID owns the port.
- MySQL `--defaults-file` must be the first argument. Option files treat `\` as an escape character, which is why placeholders expand with `/`.
- cloudflared prints the trycloudflare link *before* the tunnel is registered, and the new name takes 10–15 s to reach DNS. Opening it early makes Windows cache NXDOMAIN for minutes. So `start()` waits for "Registered tunnel connection" and then for the name to resolve through Cloudflare DNS-over-HTTPS (not the system resolver, which would poison the cache). cloudflared also logs an ERR for an empty `--config` file, so `etc\cloudflared\quick-tunnel.yml` contains `no-autoupdate: true`.
- mod_fcgid starts php-cgi with an almost empty environment. Without `SystemRoot`, PHP's random_bytes/openssl/curl fail. Its default `FcgidMaxRequestLen` (128 KB) breaks uploads and phpMyAdmin imports. Both are set in `httpd.conf.j2`. Apache and MySQL listen on loopback only. `/phpmyadmin` refuses requests carrying `CF-Connecting-IP`, because tunnel traffic arrives from 127.0.0.1 and would otherwise pass `Require local`.
- watchdog on Windows reports a deleted *folder* as a `FileDeletedEvent` (is_directory False), so the www watcher must not filter on is_directory.
- The Laragon Apache build pairs mod_ssl (built for OpenSSL 3.6.3) with 3.0.21 DLLs, which logs AH01882 at every start. It's harmless and needs matching DLLs from Apache Lounge to fix.
- Child stdout/stderr go straight to `logs\<id>.log` through an inherited handle, so logs keep flowing after varsha exits.
